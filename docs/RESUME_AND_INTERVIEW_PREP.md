## Interview talking points (STAR format)

### "Walk me through a project you're proud of."

- **Situation:** IBM SkillsBuild/AICTE internship problem statement asked for
  an "adaptive AI system for plagiarism detection that learns from
  instructor feedback" — most plagiarism tools are static string-matchers.
- **Task:** Build something that actually handles the cases string-matching
  misses: paraphrased plagiarism, AI-generated submissions, and
  contract-cheating/ghostwriting (which matches nothing online).
- **Action:** Designed three independent signals (semantic similarity,
  AI-text classification, stylometric drift), fused them with a model that
  retrains per-course on instructor verdicts, and wrapped the whole thing in
  a LangGraph agent that generates evidence-cited (not just "this is
  plagiarized") reports via IBM Granite.
- **Result:** Evaluated each signal on public benchmarks rather than
  eyeballing it — AI-text detector hit 0.95 F1/0.99 ROC-AUC on HC3;
  similarity hit 0.99 F1 on the realistic paraphrase-vs-unrelated task.

### "What was the hardest technical decision you made?"

Good honest answer, and a genuinely good one — talks about judgment, not
just execution:

> "I originally used ChromaDB for the vector search. During testing it hit
> a reproducible crash in its compiled Rust extension on my dev environment.
> Instead of fighting a native-dependency bug I didn't control, I stepped
> back and asked what the actual scale requirement was — a single course's
> submission history tops out at maybe a few thousand chunks. At that scale,
> a full ANN vector database buys you nothing; a brute-force NumPy cosine
> similarity search is sub-millisecond and removes a whole class of
> deployment risk. I replaced it, kept the same interface so nothing else in
> the codebase changed, and documented in the README exactly when you *would*
> need to swap back to a real vector DB (100K+ vectors)."

This is a strong story because it shows: (1) you hit a real bug, (2) you
didn't just brute-force around it, (3) you reasoned about actual scale
instead of defaulting to "use the trendy tool," (4) you kept the change
isolated behind an interface.

### "Tell me about a time your results weren't what you expected."

Also a strong, true story:

> "I evaluated my stylometric-drift signal — a per-student writing-style
> fingerprint meant to catch ghostwriting — on a same-author-vs-different-
> author task using real Reddit data. It came back close to chance,
> ROC-AUC ~0.55. Instead of tuning until I got a good-looking number, I
> checked the literature: classic authorship-attribution work uses 500+
> word samples because function-word-frequency features need that much text
> to stabilize; my test documents were ~40-word comments. I re-ran the eval
> with comments concatenated into ~750-word pseudo-documents — still real
> author text, just enough of it — and got a real, moderate signal, ROC-AUC
> 0.65. It's still the weakest of my three signals, and I say so in the
> README and weight it lowest in the fusion model on purpose. It's the only
> signal that can catch contract-cheating at all, so it stays in the system
> as corroborating evidence, not a standalone verdict."

If an interviewer pushes on "why is 0.65 good enough to ship" — the honest
answer is it isn't, alone; that's *why* it's fused with two much stronger
signals and weighted lowest, and why the UI always shows evidence, not a
bare score, so a human makes the final call.

### "Why does your similarity detector have two very different scores?"

> "PAWS is deliberately adversarial — pairs that share nearly every word but
> mean opposite things. A generic sentence embedding, not fine-tuned on a
> paraphrase objective, is expected to struggle on that specific benchmark —
> that's the whole point of PAWS as a stress test. So I also built a second,
> more representative evaluation: genuine paraphrase vs. an ordinary
> unrelated sentence, which is what a real plagiarism case actually looks
> like. That one scored 0.99 F1. Reporting only the flattering number would
> have hidden a real limitation; reporting only the bad one would have
> misrepresented what the system needs to do in production. I reported
> both, with the reasoning."

### If asked about IBM Granite / watsonx specifically

Be precise about what you actually ran vs. what's wired up and ready:

- If you deploy it with real watsonx.ai credentials before the interview:
  describe the real run — what model ID, what the explanation agent's
  prompt does (evidence-based, non-accusatory, hedges on low-confidence
  signals), and show the generated report text.
- If you only tested the `local` Granite backend or the template fallback:
  say that plainly — *"the client is built to swap between watsonx.ai and a
  local Granite checkpoint via one env var; I validated the orchestration
  logic end-to-end with a stub, and ran [X] against the real
  watsonx/local backend."* Don't imply a cloud run happened if it didn't —
  this is exactly the kind of claim an interviewer can ask you to
  demonstrate live.
